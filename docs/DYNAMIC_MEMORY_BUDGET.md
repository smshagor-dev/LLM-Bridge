# Live cooperative memory-budget capacity

`MemoryBudget::set_capacity(bytes)` changes the capacity used for new reservations and returns the previous capacity. Existing Reservation values keep their original byte charge and release it only on drop. Capacity may be reduced below current reservations, including to zero. Construction still requires a positive capacity.

`BudgetSnapshot` captures capacity, reserved, available and over-capacity bytes together. After shrinking 100 to 20 with 80 already reserved, the snapshot is capacity 20, reserved 80, available 0, over-capacity 60. A new positive request cannot acquire until the current total plus the request fits the current capacity. Dropping the old reservation removes the debt; increasing capacity can reopen admission. No reserved bytes disappear merely because the limit changed.

Resize, acquisition, release and snapshots use one short per-budget mutex. This replaces the earlier immutable-capacity atomic-counter loop so reservation acquisition cannot commit against an old capacity after a completed shrink. No model I/O or user consumer runs under this lock. Queue admission acquires queue state before budget state; budget methods never acquire a queue lock. The operations are synchronized/atomic as a policy, not lock-free, and no latency improvement is claimed.

The existing queued native API observes this live budget without a new FFI or numerical path. Already-queued requests remain pending if the new capacity cannot cover them; cancellation/RAII cleanup stays available. FIFO does not skip a formerly admissible head that no longer fits. Cancel that head or restore enough capacity when required. New enqueue operations above the current capacity are refused by the existing queue validation; zero capacity therefore rejects new requests while existing tickets can wait for growth. This differs from #85's explicit admission pause, which retains capacity and accepts bounded pending work. Neither mechanism interrupts already-admitted native execution.

Use `snapshot()` when the fields must describe one state. Separate `capacity()`/`reserved()` calls are individual concurrent observations. Multiple controllers must coordinate: the latest explicit resize wins. The API does not sample OS/cgroup headroom automatically, cancel active sessions, reclaim native allocations, resize a worker pool or enforce process RSS. Reserved/over-capacity bytes are cooperative accounting, not physical memory use. The private budget in #84's executor needs a separate controller interface; this change targets main's existing caller-owned MemoryBudget and queued generation.

## Validation

Unit regressions cover retained charges/debt after shrink, zero/growth behavior, concurrent post-shrink refusal, overflow/zero input and FIFO head handling. The real pinned Q8 contract holds a pending request behind an existing reservation, shrinks capacity to zero, drops the old reservation and requires the request to stay pending. Restoring capacity admits it; at its first-logits callback the session shrinks capacity again, retains its full native reservation and finishes with complete-output/all-FP32-logit hashes equal direct execution. After cleanup there is zero reserved/debt at zero capacity. A new missing-model request is refused before opening, old pending work cancels after shrink, and subsequent growth permits another identical native result.

Reproduce with `cargo run --release -p llmbridge-core --features native --example resized_budget_contract -- models/stories15M-q8_0.gguf`. These are tiny-model accounting/correctness results, not throughput, physical2GB, immediate RSS reduction or large-model feasibility evidence. Existing explicit Linux process limits and authentication remain separate and unchanged.
